> **Goal:** tag *who in our church has the resource or skill to help* with a given need, so routing ([[routing-and-functions]]) can point to a specific person — the "resource priority pass."

## The gap

The current Membership Database (`content/reference/`) has **no fields** for profession, skills, spiritual gifts, owned resources (truck, tools), availability, or capacity. It only has:

- `Office` (Pastor / Elder / Deacon / Staff)
- `Fellowship Group` (life-stage)
- `Ministry Group` (Word, Worship, Mission, Children, Youth, Nursery, Livestream)
- `Deacon Department` (Administration, Operation, Communication, Finance + sub-lanes: Welcome, Kitchen, Coffee, IT, PEP)

The Service Sign-Up roster names ~81 servers across 20 areas, but again by role, not by skill/resource.

## To design here

- The **resource/skill data model**: what tags to capture (profession, certifications/skills, equipment/resources, languages, availability, capacity, willingness flags).
- How to **collect** it (a member skills survey / sign-up) without burdening members or duplicating the existing DB.
- How tags map to [[request-taxonomy|request types]] so a need → a ranked list of helpers.
- Privacy: this data is **internal**, never published; lives with the future web app, not this wiki.
